Añadir diagramas al visor sin retrasar la lectura del Markdown. Rust seguirá procesando el documento; una biblioteca local convertirá los bloques Mermaid en SVG dentro del WebView.

01

Propuesta y alcance

Reconocer los bloques cercados con el lenguaje mermaid y dibujarlos después del primer pintado del texto. Un módulo src/mermaid.ts coordinará la carga, el renderizado y los errores. La biblioteca se empaquetará con la app, con versión exacta y dependencias fijadas en pnpm-lock.yaml.

La primera entrega debe renderizar los diagramas que ya existen en docs/: flujos y secuencias. Añadir como casos de aceptación estados, clases y relaciones entre entidades. Documentar el conjunto validado; no prometer todos los tipos de Mermaid sin probarlos.

El lector conservará el código original en un desplegable "Ver código". Ante sintaxis inválida, un tipo no admitido o un límite excedido, mostrará ese código y un aviso junto al bloque. El resto del documento seguirá disponible.

Esta entrega cubre visualización de solo lectura. La exportación, el editor en vivo y las acciones de clic dentro de los diagramas quedarían para una ampliación posterior.

03

Arquitectura resultante

El HTML de Rust conserva cada definición como texto escapado dentro de un bloque de código. La interfaz extrae textContent, pide el SVG a Mermaid y valida ese resultado antes de incorporarlo al documento. El SVG generado pertenece a una segunda ruta de limpieza, porque se crea después de ammonia.

04

Cómo implementarlo

  1. Resolver versión y compatibilidad

    Probar una versión exacta de Mermaid en los WebViews soportados. La documentación actual de Mermaid 12 indica ES2024 y Safari 17.4 como referencia mínima. El target ES2020 del proyecto no corrige APIs de navegador ausentes. Requisitos oficiales.

    No elevar silenciosamente el mínimo de macOS 10.15. Si la versión probada exige otro mínimo, acordar y documentar el nuevo soporte antes de adoptarla; una versión anterior requiere revisar mantenimiento y avisos de seguridad.

    Salida: versión fijada, motores mínimos y tipos de diagramas verificados.

  2. Empaquetar dependencias para el WebView

    Añadir Mermaid y DOMPurify como dependencias de ejecución, y esbuild como dependencia de desarrollo. En frontend.mjs, ejecutar tsc --noEmit y luego esbuild con bundle: true, format: 'esm', splitting: true y outdir: 'dist'. Mantener app.js como entrada de index.html, con type="module".

    Conservar la copia de HTML/CSS, la limpieza en release y el modo de seguimiento compatible con Sprite. El seguimiento recompilará los módulos nuevos; Tauri recargará dist/. Revisar la resolución de módulos de TypeScript y registrar todos los chunks en el paquete. División de código en esbuild.

    Salida: instalación empaquetada que renderiza con la red desconectada.

  3. Preservar e identificar los bloques

    Añadir una prueba Rust que transforme ```mermaid en <pre><code class="language-mermaid"> con contenido escapado. Cubrir <, &, Unicode y varios bloques. Confirmar el comportamiento real de ammonia antes de ampliar permisos.

    Buscar solo pre > code.language-mermaid dentro del artículo. Leer textContent, nunca innerHTML. Mantener la sintaxis canónica en minúsculas y probar bloques con información adicional. Los demás lenguajes conservan su presentación actual.

    Salida: detección precisa sin añadir campos o comandos al IPC.

  4. Añadir el coordinador y conectarlo con la apertura

    Definir renderMermaid(root, generation, theme) en src/mermaid.ts. Salir sin importar la biblioteca si no hay bloques. Guardar una única promesa de import('mermaid'); reiniciarla si la carga falla para permitir un reintento.

    Crear una cola global con un renderizado activo. Configurar el tema dentro de esa cola y usar un identificador de SVG único por intento. Comprobar generación y isConnected antes y después de cada operación asíncrona. Tras un error, limpiar el contenedor temporal y continuar con el siguiente bloque.

    Iniciar el trabajo después de dar al texto una oportunidad de pintarse. openDocument no espera el renderizado; cada tarea captura sus propios errores. La API render permite controlar la inserción del SVG. API oficial.

    Salida: varios diagramas correctos; un bloque inválido no interrumpe la lectura.

  5. Aplicar la política de SVG y completar la experiencia

    Encapsular limpieza, estilos y validación en sanitizeDiagramSvg. Montar solo su resultado. Crear los avisos y el código mediante APIs del DOM y textContent. Añadir el contenedor con desplazamiento horizontal, el desplegable de código y etiquetas accesibles.

    Actualizar pruebas, ejemplos y documentación. Cambiar la afirmación del README sobre ausencia de dependencias de ejecución; describir las bibliotecas locales y el conjunto de diagramas validado.

    Salida: controles de seguridad y criterios de aceptación del apartado 08 satisfechos.

Ver el flujo orientativo del coordinador
// Esquema de diseño. Los helpers se implementan en mermaid.ts.
async function renderMermaid(root, generation, theme) {
  const blocks = collectMermaidBlocks(root);
  if (blocks.length === 0) return;
  const mermaid = await loadLocalMermaid();

  for (const block of blocks) {
    await renderQueue.add(async () => {
      if (!isCurrent(generation, block)) return;
      try {
        enforceLimits(block.source);
        mermaid.initialize(trustedConfig(theme));
        const { svg } = await mermaid.render(uniqueId(), block.source);
        if (!isCurrent(generation, block)) return;
        const safeSvg = sanitizeDiagramSvg(svg);
        mountDiagram(block, safeSvg); // conserva source para "Ver código"
      } catch (error) {
        if (isCurrent(generation, block)) showBlockError(block, error);
      } finally {
        cleanupTemporaryRender();
      }
    });
    await yieldToBrowser();
  }
}
05

Ciclo de renderizado y aperturas simultáneas

Separar requestId, que identifica una petición de apertura, de renderGeneration, que identifica el documento visible y su tema. Una apertura cancelada o fallida conserva el documento anterior; no debe dejar sus diagramas cancelados para siempre.

Incrementar la generación al reemplazar el artículo o al cambiar el tema. Cancelar las tareas pendientes de generaciones anteriores. Un renderizado en curso puede terminar, pero su resultado se descarta y se limpia si dejó de ser vigente.

06

Seguridad y política de contenido

Configuración controlada por la app

Usar securityLevel: 'strict', startOnLoad: false, htmlLabels: false y suppressErrorRendering: true. El modo estricto desactiva las acciones de clic; no llamar a bindFunctions. Nivel de seguridad.

Preservar las claves protegidas por defecto de secure y añadir htmlLabels, themeCSS, dompurifyConfig, theme y themeVariables. Rechazar en la primera entrega frontmatter y directivas de configuración por bloque con un aviso. Probar que no pueden cambiar estas reglas. Opciones protegidas.

SVG como contenido no confiable

Limpiar con DOMPurify usando perfiles SVG y filtros SVG; bloquear foreignObject, scripts, eventos, enlaces y recursos externos. Mantener referencias locales #id para marcadores. DOMPurify admite SVG, pero la restricción de recursos y CSS requiere una política adicional de la app. Soporte de DOMPurify.

Validar href, xlink:href y valores CSS que cargan recursos. Permitir solo referencias al propio SVG. No añadir SVG crudo de Markdown a las etiquetas aceptadas por ammonia.

La CSP es una condición de entrega. Los SVG de Mermaid incluyen estilos dinámicos que style-src 'self' puede bloquear. Abrir style-src con 'unsafe-inline' afectaría también al HTML del documento. La prueba debe usar la CSP real de Tauri, no solo un navegador sin restricciones.

Propuesta: conservar las directivas existentes y añadir un nonce a cada elemento <style> aprobado del SVG. Obtener el nonce de un recurso de confianza que Tauri procese, y aplicarlo durante la limpieza. Antes de montarlo, analizar el CSS, limitar selectores al identificador único del SVG y rechazar @import, URLs externas y reglas fuera del diagrama. Eliminar atributos style o trasladar sus propiedades admitidas a reglas con ese nonce.

Probar que el saneador conserva únicamente el CSS aprobado y sus nonces. Si la versión de Tauri no facilita un nonce reutilizable o los tipos de diagramas no funcionan al transformar sus estilos, esta estrategia necesita revisión antes de integrar. Los hashes generados al compilar no autorizan CSS que solo se conoce al abrir un archivo. Cómo Tauri aplica la CSP.

Usar un contenedor temporal visible para el motor de diseño pero fuera de la pantalla; display:none puede impedir medir etiquetas. Mantenerlo fuera del artículo, con aria-hidden="true" y limpieza en finally. La limpieza posterior del SVG no protege ese DOM temporal: revisar el comportamiento de la versión fijada bajo CSP y configuración estricta. Si esa fase permite contenido activo, el prototipo no cumple el plan.

Son valores propuestos para medir y ajustar. Promise.race con un temporizador no detiene un cálculo síncrono que bloquea el WebView. Los límites reducen el riesgo, pero no garantizan un tiempo máximo; una cancelación fuerte requiere aislamiento y una arquitectura adicional.

07

Lectura, temas y rendimiento

  • Mostrar el código mientras el diagrama se prepara. Un error se anuncia junto al bloque y conserva la fuente, sin activar el error global de apertura.
  • Responder a matchMedia('(prefers-color-scheme: dark)'). Guardar la fuente original y volver a renderizar al cambiar el tema, usando otra generación y la misma cola.
  • Usar fuentes del sistema y esperar a document.fonts.ready cuando proceda. Verificar etiquetas largas, acentos y tamaños del SVG en los tres motores.
  • Conservar viewBox, evitar recortes y ofrecer desplazamiento horizontal para diagramas anchos. Probar la ventana mínima de 400 píxeles y ampliación al 200 %.
  • Conservar o crear title y desc accesibles, y usar un nombre de diagrama si la fuente no lo trae. El desplegable "Ver código" funciona con teclado y no debe perder el foco al cambiar de tema.
  • Mantener content_painted para el texto. Medir por separado carga de Mermaid, tiempo de cada SVG, final del lote y tamaño añadido a la distribución.
  • Comparar apertura sin Mermaid, con un diagrama y con 50 diagramas. No fijar una mejora de tiempo o un tamaño sin medir el paquete release.

La primera entrega procesa los bloques en orden. Si los documentos grandes retrasan el uso del lector, una segunda iteración puede priorizar diagramas próximos a la vista con IntersectionObserver. No hace falta añadir caché de SVG al primer cambio.

Criterios para considerar terminada la función

  • Los diagramas existentes de docs/ se ven correctamente y funcionan sin conexión.
  • Un documento sin Mermaid no carga la biblioteca; su texto conserva la medición de apertura.
  • Un bloque inválido o limitado conserva el código y no afecta a otros diagramas.
  • Aperturas A/B, cancelación y cambios de tema no insertan SVG obsoleto ni dejan residuos temporales.
  • Los diagramas respetan la CSP y no ejecutan acciones ni cargan recursos definidos por el documento.
  • La lectura con teclado, el código original y ambos temas funcionan en ventanas estrechas.
  • Los paquetes incluyen todos los recursos y se documentan los mínimos de sistema comprobados.

  • esbuild: empaquetado con división de código.
  • DOMPurify: limpieza de HTML y SVG.
